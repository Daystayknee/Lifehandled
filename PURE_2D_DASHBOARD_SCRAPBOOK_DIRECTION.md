# Pure 2D Direction: Dashboard + Scrapbook + Social Life Sim

## Decision

We are committing the next visual production phase to **pure 2D** presentation (UI-first, card-based, portrait-driven), while keeping the current runtime simulation architecture.

## Why pure 2D is the right move for this project

### 1) Better style control
A pure 2D pipeline gives direct control over an anime × semi-real visual identity, glossy UI treatment, scrapbook framing, and social-feed composition.

### 2) Faster content throughput
2D supports much faster production and iteration for:
- hairstyles
- face/body feature parts
- clothing sets
- animal portraits/icons
- event illustrations
- UI cards and feed posts

### 3) Best fit for the current runtime architecture
The existing systems are already session and state driven:
- zone travel and location state
- world/economy/NPC simulation ticks
- event, memory, relationship, and reputation state
- HUD/interaction panel presentation flow

This naturally maps to a **node-map + dashboard + event-card** interface without requiring free-walk 3D scenes.

## The 4 visual layers to implement next

## 1. Main Dashboard UI (Primary gameplay surface)
This becomes the default play screen and life-control center.

### Must-show modules
- Character portrait (dynamic layered 2D)
- Needs + status
- Money/income/rent pressure
- Time/day/weather/calendar/holiday
- Current zone and safety context
- Household tension/status
- Reputation snapshot
- Social feed/life journal teaser
- Quick actions row

### Integration points (existing runtime)
- `SessionContextRegistry.Current`
- `GameSessionContext` fields for day/weather/reputation/tension/events
- Existing use-cases triggered by UI buttons and action cards

### Deliverables
- Dashboard layout prefab(s)
- Data-binding presenter/controller
- Modular widget prefabs (Needs, Economy, Time/Weather, Household, Social)

---

## 2. 2D Character Portrait System (Layered sprite architecture)
Replace 3D avatar dependency with composited 2D layered portraits.

### Core rule
Use **layered sprite parts**, not full pre-rendered combinations.

### Feature categories to support
- Face structure: face, eyes, nose, mouth, brows, ears
- Skin detail overlays: freckles, beauty marks, vitiligo, etc.
- Hair system: type, length, style, front/back overlays
- Body proportions: fat/muscle/chest/waist/hips/thigh/calf/hands/feet (represented as curated 2D shape variants)
- Clothing overlays by slot/category

### Runtime data approach
- Keep existing genetics/appearance model as source inputs.
- Add a portrait projection layer that maps `CharacterData` + appearance traits into selected sprite part IDs.
- Store selected part IDs in save-safe, migration-friendly fields.

### Deliverables
- Portrait part taxonomy (ID convention)
- Layer order spec
- Resolver/binder that selects parts from runtime character state
- Fallback/default part strategy for compatibility

---

## 3. Zone / Travel / Event Panels (Node-map + card scenes)
Zones become interactive 2D panels/cards instead of free movement spaces.

### Flow
1. Player selects a map node (zone)
2. Travel use-case executes
3. Zone panel opens with:
   - NPCs present
   - wildlife/resources
   - risk/weather modifiers
   - zone actions
4. Event cards/reaction text render outcomes

### Runtime alignment
- Built directly on `TravelToZoneUseCase`
- Reads already-simulated zone state, events, NPC pools, and weather
- Uses existing social/drama/reputation outputs as action consequences

### Deliverables
- World map node view
- Zone panel template
- Event card renderer
- Action-to-use-case routing table

---

## 4. Scrapbook / Social Feed / Journal (Emotional history layer)
This becomes the long-term memory surface of the game.

### Content targets
- Day summaries
- NPC posts and rumor propagation highlights
- Event memory entries
- Collectible discoveries and recipes
- Milestone pages and life chapters

### Runtime alignment
- Ingests data from memory/drama/reputation events already generated by use-cases
- Consumes existing save-compatible timeline/day/session fields

### Deliverables
- Feed entry schema (type, source, tone, visibility)
- Journal page templates (daily, milestone, collection, social)
- Entry generation service from runtime events

## Incremental implementation order (architecture-safe)

### Phase A — Dashboard foundation
- Build dashboard shell + widget binding against current context.
- Keep existing HUD alive in parallel until parity is reached.

### Phase B — Portrait compositor MVP
- Add layered portrait renderer with limited initial part library.
- Wire player + first NPC portrait variants in dashboard and event cards.

### Phase C — Zone card panels + event scenes
- Introduce node map view and card-based zone detail panels.
- Route existing travel and action use-cases through panel buttons.

### Phase D — Scrapbook/feed alpha
- Generate daily and event entries from current simulation outputs.
- Add social rumor and relationship milestone entries.

### Phase E — Content scale-up
- Expand portrait part sets, clothing lines, event art, wildlife cards, and journal templates.

---

## Technical guardrails

- Do **not** break save compatibility; all new fields require defaults/migration.
- Keep simulation use-cases presentation-agnostic (UI reads outputs; no UI coupling in core logic).
- Prefer adding projection/adapter layers over rewriting core domain models.
- Keep each UI layer shippable independently with clear fallback states.

---

## “Definition of Alive” checkpoint for this direction
The direction is successful when a player can:
1. Start in dashboard,
2. travel via map node,
3. resolve an event card with portrait reactions,
4. observe immediate NPC/reputation/household effects,
5. and find the day’s story reflected in the scrapbook feed.

This checkpoint should be treated as the first complete vertical UX loop for the pure 2D product identity.
